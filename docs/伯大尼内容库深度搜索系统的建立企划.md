# 伯大尼内容库深度搜索系统的建立企划

> **版本**：讨论稿 v0.3（非最终版，可随时修改）  
> **日期**：2026-07-06

---

## 用三句话说明白

1. **我们要建什么**：一套**独立的深度搜索系统**，支撑「发现主题 → 找全材料 → 整理成系列」整条工作流；核心是**把圣经启示的关系结构化**，检索是手段，系列内容是成果。
2. **它包含三种能力**：**挖掘**（给范围，找出候选主题词和发展脉络）、**检索**（给主题词，找全相关段落）、**整理**（把材料排成系列大纲和文章，严格引用原文）。
3. **第一步做什么**：先做成 **API 引擎**（命令行也能用），优先打通**检索**；挖掘和整理分步跟上；**暂时不做网页**。

---

## 一、为什么要建这个系统？

### 1.1 普通搜索不够用什么

| 现有工具 | 能做什么 | 做不到什么 |
|----------|----------|------------|
| **PanSearch 主站搜索** | 关键词 → 段落列表 | 找不到「字不同、义相近」的内容；无法围绕主题**找全** |
| **问答站（QA）** | 回答一个问题，约 20～30 条段落 | 召回太少，不适合系列研究 |
| **纲目制作（KG-RAG）** | 根据负担说明做纲目 | 产品是「做纲目」，不是「挖主题 + 深搜 + 做系列」 |
| **进展纲目（progress_outline）** | 进展75、新增词条 | **另一条产品线，与本项目无关** |

### 1.2 深度搜索要解决什么

圣经知识不是普通文档：同主题多种说法（帐幕/圣殿、活水/那灵）、主题有**发展脉络**（预表→应验、首次出现→完成）、大量内容**字面上对不上**但意义相关。

所以深度搜索 ≠ 搜关键词，而是：

> **理解主题 → 追踪启示如何发展 → 找全相关材料 → 按神学逻辑整理成系列**

### 1.3 三个应用场景（系统要支撑的）

| 场景 | 举例 | 系统哪部分负责 |
|------|------|----------------|
| **1. 挖掘主题词** | 给「贯穿整本圣经的主题词」→ 得到水、石头、光、殿… | **挖掘（discover）** |
| **2. 全面准确检索** | 给定「水」→ 找全职事讲解 + 相关经文脉络 | **检索（run）** |
| **3. 整理成系列内容** | 「水」→ 5～10 篇可发布文章，每篇有纲、有引用 | **整理（synthesize）**（项目层，后期） |

第一个具体项目：**贯穿圣经的主题词系列**（约 30～40 个主题，每主题 5～10 篇）。  
系统本身要**通用**，以后别的项目也能只用其中部分能力。

### 1.4 与 progress_outline 的边界

| | progress_outline | 本项目 |
|---|------------------|--------|
| 做什么 | 进展75纲目、新增词条 | 深度搜索系统 + 主题系列 |
| 关系 | **不能**混路由、页面、流程 | 可参考「按篇题筛选」思路，代码独立 |

## 二、我们要建的是什么？

### 2.1 一句话定义

**伯大尼内容库深度搜索系统** = 独立平台，内含 **挖掘、检索、（后期）整理** 三种能力，基于圣经知识与职事信息库，把人机协同的「主题研究生产线」跑通。

可以把它想成：

> **神学研究的深度助手**——先帮你想「该研究哪些题目」，再帮你在书库里**找齐**材料，最后帮你**按启示发展线**排成系列（人始终审校）。

### 2.2 它不是什么

- ❌ PanSearch 主站里的一个新菜单  
- ❌ 问答站、进展纲目工具  
- ❌ 第一步就要做的「主题系列发布网站」  
- ❌ 只靠关键词匹配的普通搜索  

### 2.3 它和 PanAI 主站的关系

```
┌─────────────────────┐       ┌─────────────────────────────┐
│  PanAI 主站          │       │  深度搜索系统（新建）          │
│  普通搜索、纲目…      │       │  挖掘 + 检索 +（后期）整理    │
│  有自己的网页         │       │  第 1 步只有 API              │
└──────────┬──────────┘       └──────────────┬──────────────┘
           │         共用底座，各跑各的         │
           └────────────────┬────────────────┘
                            ▼
              Elasticsearch（kg-rag_* 职事语料）
              圣经 JSON（QA 站，待统一接入）
              back_shared（检索、向量、精排）
              Neo4j（概念图谱，部分已有）
```

**共用**：书库、底层检索代码、概念图谱  
**不共用**：网站入口、登录、前端、产品功能  
**参照**：问答站 `back_qa` 的独立部署方式（自己的 `main.py`、自己的端口）

## 三、知识库分三层（重要）

系统不是只搜「职事信息」，而是**圣经知识 + 职事信息**两条腿。现网强弱不同，要心里有数。

| 层级 | 内容 | 现网状态 | 深度搜索怎么用 |
|------|------|----------|----------------|
| **A. 圣经知识库** | 经节、书卷章结构；远期：多译本、原文词根 | ⚠️ QA 站有内存圣经 JSON，**未统一入库** | 挖主题、对经文、演化链的**主战场** |
| **B. 职事信息库** | 李常受、倪柝声等职事信息（`kg-rag_*`） | ✅ 较完整，有 chunk + 向量 | **第 1 步检索的主底座** |
| **C. 概念图谱** | 主题概念、关键经文、部分关系（Neo4j） | ⚠️ 有**种子图谱**，非全自动 | 挖词、扩检索、演化链的**增强层** |

**第 1 步现实做法**：检索先在 **B 层（职事库）** 跑通；挖掘和演化链设计时**预留 A、C 层接口**，避免以后推倒重来。

## 四、系统三种能力（核心设计）

三种能力在**同一个系统**里，不是三个独立产品。

```
┌────────────────────────────────────────────────────────┐
│              伯大尼内容库深度搜索系统                      │
│                                                        │
│   ┌──────────────┐  ┌──────────────┐  ┌─────────────┐ │
│   │ 挖掘 discover │  │ 检索 run      │  │ 整理 synthesize│ │
│   │              │  │              │  │  （后期）     │ │
│   │ 给范围        │  │ 给主题词      │  │ 给材料包      │ │
│   │ ↓            │  │ ↓            │  │ ↓           │ │
│   │ 候选词        │  │ 大量段落      │  │ 系列大纲/文章  │ │
│   │ + 演化链草案  │  │ + 覆盖报告    │  │ + 严格引用    │ │
│   └──────────────┘  └──────────────┘  └─────────────┘ │
└────────────────────────────────────────────────────────┘
```

### 4.1 挖掘（discover）—— 对应场景 1

**输入**：大致范围 + 条件（例如：「贯穿圣经的主题词」「旧约新约都要出现」「职事六阶段都有材料」）

**输出**：

- 候选主题词列表（如水、石头、光、殿…），每条带**依据**（出现频次、阶段分布、关键经文等）
- **主题演化链草案**（例如：帐幕 → 圣殿 → 基督 → 召会 → 新耶路撒冷）

**怎么挖**（多信号组合，不是单一词频）：

| 手段 | 说明 | 现网 |
|------|------|------|
| 职事语料统计 + 篇题匹配 | 在全库篇题、chunk 里找反复出现的意象词 | 可参考 `build_topic_catalogs` 思路 |
| 概念图谱 | Neo4j 里已有概念及其关键经文 | 有种子，覆盖有限 |
| 经文首次出现 / 跨卷关联 | 某主题在摩西五经、先知书、新约的出现 | QA 圣经数据有，待统一接入 |
| 语义聚类 | 把相近语义的经文/段落聚成簇，再命名 | **要新建** |
| LLM 归纳命名 | 给聚类簇起主题名、写简短理由 | 有 LLM 能力，需专用流程 + **必须有证据** |
| 预表→应验线索 | 吗哪→生命供应、铜蛇→十字架等 | **要新建**（图谱或规则 + 人工审校） |

**原则**：机器出候选，**人审定稿**；LLM 不能凭空造词，每条候选要有可查证的依据。

### 4.2 检索（run）—— 对应场景 2

**输入**：检索任务单（见第五节），核心是**一个已定主题词**（如「水」）及扩展词、过滤条件

**输出**：约 200～500 条相关段落 + 覆盖报告（六阶段、生命读经各卷等）+ 可复查的 `run_id`

**检索是「多路混合」，不只是关键词 + 向量**：

| 检索路 | 做什么 | 现网 |
|--------|--------|------|
| 路 1 关键词 | BM25 精确匹配 | ✅ `back_shared/retrieval` |
| 路 2 语义向量 | 找字面不同、意思相近的段落 | ✅ 同上 |
| 路 3 图谱扩词检索 | 用 Neo4j 关联概念扩展搜索词后再搜 | ✅ QA/KG-RAG 已有类似能力 |
| 路 4 图谱关系检索 | 沿概念关系、预表边拉相关经文与段落 | **要新建** |
| 路 5 演化链节点检索 | 演化链上每一环单独召回，再合并 | **要新建**（依赖演化链对象） |

各路结果 → 合并去重 → 每篇条数上限 → **精排 1 次** → 输出。

### 4.3 整理（synthesize）—— 对应场景 3（后期）

**输入**：某主题的材料包（段落 + 演化链 + 覆盖报告）

**输出**：系列大纲、分篇草稿，**每一段论述必须标注出处**（复用 KG-RAG「逐字引用、LLM 只选材排列」原则）

**大纲不按随便聚类，而要支持多种结构模式**：

| 模式 | 适用 | 举例 |
|------|------|------|
| `evolution_chain` | 主题有清晰发展线 | 殿：伊甸园 → 会幕 → 基督 → 召会 → 新天新地 |
| `testament_span` | 预表与应验 | 旧约预表 → 新约完成 |
| `ministry_stage` | 职事阶段覆盖 | 六阶段各选材料 |
| `topic_cluster` | 补充性分组 | 纯语义相近的段落归一组 |

**第 1 步不做整理**；架构和数据模型要预留。

### 4.4 核心对象：主题演化链

除「候选词」「段落」「文章」外，增加一类核心数据：

**主题演化链** = 一个主题在圣经历史中如何展开（例如「生命」：生命树 → 吗哪 → 活水 → 基督 → 那灵 → 生命河）

- 挖掘时：产出**草案**，人工审校  
- 检索时：链上每个节点可触发一路召回  
- 整理时：可按链上分讲

## 五、人机协同工作流（实际怎么用）

以第一个项目「贯穿圣经的主题词」为例：

| 步骤 | 人做什么 | 系统做什么 | 产出 |
|------|----------|------------|------|
| **1. 发现** | 输入范围：「贯穿圣经的主题词」 | `discover`：候选词 + 演化链草案 + 依据 | 待审主题表 |
| **2. 审定** | 勾选、改名、删词，定 30～40 个 | 写入主题注册表 | 定稿主题库 |
| **3. 篇目**（项目层） | 审校相关篇题列表 | 规则/脚本筛篇目（可参考 progress_outline 思路） | approved 篇目 |
| **4. 深搜** | 确认或微调检索任务单 | `run`：高召回段落 + 覆盖报告 | 材料包 |
| **5. 复查** | 看缺哪些阶段/书卷，调任务单再跑 | 同 `run`，可多次 | 完善材料包 |
| **6. 结构** | 选大纲模式（演化链/预表应验等） | 分组 + 排讲次 | 系列大纲 |
| **7. 成文** | 审校神学表述与引用 | `synthesize`：填内容，强制标注出处 | 系列草稿 |
| **8. 发布** | 终审定稿 | （发布站，更后期） | 可读者系列 |

**第 1 步（API 引擎）重点交付**：`run` 全流程；`discover` 做最小可用；步骤 6～8 以后再做。

## 六、检索任务单（SearchProfile）

每次**检索**提交一份任务单（YAML 或 API JSON）：

| 字段 | 举例（「水」） |
|------|----------------|
| 主搜索词 | 水、生命、流动、赐活 |
| 扩展词 | 活水、河水、涌流 |
| 图谱扩展 | Neo4j 中与「水」相关的概念 |
| 演化链节点（可选） | 创造之水、审判之水、救赎之水、活水江河… |
| 搜哪些库 | 默认全部 `kg-rag_*`，可收窄 |
| 篇目白名单（可选） | 主题项目 L3 审校后的篇目 |
| 排除词 | 避免误命中 |
| 上限 | 例如最多 400 条，每篇最多 5 条 |
| 覆盖统计 | 六阶段、生命读经 66 卷 |

同一份任务单 = 可保存、可复查、可改后再跑。

### 一次检索的执行过程（简化）

```
任务单 → 展开搜索词（含图谱、演化链节点）
      → 多路并行检索（关键词 + 向量 + 图谱…）
      → 合并去重 → 过滤 → 每篇上限
      → 精排 1 次 → 覆盖统计 → 返回 run_id + 段落列表
```

### 和问答站的区别

| | 问答站 | 本系统检索 |
|---|--------|------------|
| 目的 | 答一个问题 | 为一个主题找全材料 |
| 条数 | ~20～30 | ~200～500 |
| 混合程度 | 关键词+向量；图谱主要扩词 | **多路混合**（含图谱关系、演化链） |
| 产出 | 一段答案 | 可复查的材料包 |

## 七、底座现状：七步蓝图对照

有人用七个步骤描述完整圣经知识系统。对照 copypan **现网**，避免误以为「都已做好」：

| 步骤 | 内容 | 现网 | 本系统要做什么 |
|------|------|------|----------------|
| 1 数据准备 | 圣经、注解、神学著作等入库 | ⚠️ 职事较全；圣经未统一入深搜库 | 第 1 步先用职事库；圣经库逐步接入 A 层 |
| 2 切分结构化 | 经节、段落、主题单元 | ⚠️ 职事 chunk 有；经节级未统一 | 复用 `chunking_full`；经节级后期补 |
| 3 知识图谱 | 实体关系、预表应验 | ⚠️ 种子概念图谱，非全自动 | 先用种子 + 半自动扩展；全自动为远期 |
| 4 向量化 | Embedding | ✅ 职事 kg-rag 大体完成 | 直接复用 |
| 5 主题挖掘与演化链 | 自动发现主题词 + 发展脉络 | ❌ 基本没有 | **`discover` 要新建** |
| 6 混合检索 | 关键词+语义+图谱+… | ⚠️ 关键词+语义有；图谱仅扩词 | **`run` 要扩展多路** |
| 7 AI 整理成系列 | 大纲、课程、引用 | ⚠️ QA/KG-RAG 有生成，未接本流水线 | **`synthesize` 后期新建** |

## 八、技术方案

### 8.1 新建什么、放在哪

独立后端 **`back_deep_search`**（与 `back_qa` 同级），**不**挂到 PanAI 主站。

```
copypan/
├── back_deep_search/           ← 新建
│   ├── main.py                 ← 独立启动，端口如 8002
│   ├── deep_search/
│   │   ├── discover.py         ← 挖掘
│   │   ├── orchestrator.py     ← 检索编排
│   │   ├── models.py           ← 任务单、演化链等
│   │   ├── coverage.py
│   │   ├── storage.py
│   │   └── cli.py
│   ├── profiles/examples/      ← water.yaml、stone.yaml
│   └── DEPLOY.md
├── back_shared/                ← 已有，直接调用
├── back_qa/                    ← 独立部署参考
└── docs/                       ← 本文档
```

第 1 步**不建**网页（`front_deep_search` 留第 2 步）。

### 8.2 API（第 1 步）

| 接口 | 能力 | 优先级 |
|------|------|--------|
| `GET /api/health` | 健康检查 | 必做 |
| `POST /api/deep_search/run` | **检索** | 必做（第 1 步核心） |
| `GET /api/deep_search/runs/{id}/…` | 查历史检索结果 | 必做 |
| `POST /api/deep_search/validate` | 校验任务单 | 必做 |
| `POST /api/deep_search/discover` | **挖掘** | 第 1 步末期或 1b，最小可用 |
| `POST /api/deep_search/synthesize` | **整理** | 第 3 步 |

鉴权：第 1 步用 API Key；完整登录第 2 步再做。

### 8.3 存什么

第 1 步用 **SQLite** 保存：检索/挖掘任务单、运行记录、段落结果、覆盖报告、演化链草案。  
多人协作量大时换 PostgreSQL，接口不变。

### 8.4 明确不照搬的技术

| 别人常提 | 我们的选择 | 原因 |
|----------|------------|------|
| 另建 Milvus / Weaviate | **不用**，继续 ES 向量 | 现网已跑通 |
| LangChain / LlamaIndex | **不引入** | 自研 orchestrator 更清晰可控 |
| 一步全自动建全文图谱 | **不做** | 先用种子图谱 + 半自动，远期再扩 |

## 九、分阶段实施计划

### 第 1 步：API 引擎（当前，约 2～3 周）

**1a 检索（优先）**

| 顺序 | 任务 | 验收 |
|------|------|------|
| 1 | 独立服务能启动 | `/api/health` 正常 |
| 2 | 检索任务单格式 | YAML 加载校验通过 |
| 3 | 多路召回：关键词 + 向量 + 图谱扩词 | 「水」多路结果能合并 |
| 4 | 去重、每篇上限、精排 1 次 | ≤400 条，单篇 ≤5 条 |
| 5 | 覆盖报告（六阶段 + 生命读经） | 能看出缺哪里 |
| 6 | API + CLI | curl / 命令行跑通 |
| 7 | 试点「水」「石头」实跑 | 各 ≥200 条，六阶段有命中 |

**1b 挖掘（紧跟或交错）**

## 十、上层业务项目怎么用本平台

**主题系列**是第一个客户，不是平台本身：

```
主题系列项目                     深度搜索系统
────────────                    ────────────
定范围 ──────────────────────→  discover（挖词+演化链草案）
人审定稿主题表
筛篇目（项目自己的 L2）
组装任务单 ──────────────────→  run（深搜段落）
人看覆盖、调参、再跑
选大纲模式、审分组 ────────────→  synthesize（后期）
人审校、发布
```

以后**项目 B** 可以只用 `run`，不用 `discover`；都在同一平台里，不重复造轮子。
