# PanAI 4.0 恢复本圣经索引方案

- 版本：v0.1（2026-09-29 初稿，待 Srey 审阅）
- 范围：ES 规划第 2 项——恢复本圣经经文 + 恢复本纲目，合成**一个** ES 索引
- 依据：`docs/panai4_es/bible_outline_probe.md`、`bible_chunk_sim.md`、`bible_chunk_sim_v2.md`（全部数字均为实测）
- 姊妹方案：`docs/panai4_es/chunks_es_plan.md`（纲目索引），本方案与其保持一致的字段命名、chunk_id 规则与向量化配置

> **不涉及注解。** 第 3 项已与领导确认使用 `map_note`，本方案完全不碰 sqlite 里的 `footnote_all_gb_27` / `foot_all_gb_28`。

## 〇、总则

沿用纲目索引的两条总则：

1. **chunk_id 只用于唯一标识与相等比较，任何代码都不得解析它。** 所有信息一律从显式字段取。
2. **块必须自带身份。** 每一块的 `text` 第一行写明卷名与经文范围，生成端拿到就知道出处，不依赖检索层补。

## 二、坐标与推导规则

### 2.1 统一坐标键

五张表共用同一套坐标：书 / 章 / 节 / 上下。

```
key = section_code * 1000000 + segment_code * 10 + unit_code
```

| 表 | 书 | 章 | 节 | 上下 |
|---|---|---|---|---|
| `verse_all_final_gb_26` | `chapter_code` | `section_code` | `segment_code` | `unit_code` |
| `verse_all_paragraph_08` | `chapter_code` | `section_code` | `segment_code` | `unit_code` |
| `outline_all_gb_25` | `chapter_code` | `related_chapters` | `related_number` | `related_section_code` |

`unit_code` / `related_section_code`：**0 = 整节，1 = 上，2 = 下**。

实测全书 76 节被拆成上/下（经文表 unit 1 与 2 各 76 条，成对）；纲目表 `related_section_code` 为 1 的 13 条、为 2 的 86 条。

> 纲目表的列名与其他表不一致（`related_chapters` 实为章、`related_section_code` 实为上下），这是原数据的命名，照用即可，但代码里必须注释清楚。

### 2.2 诗篇特例

纲目表中 `related_number = 0` 的实测 **6 条**（诗篇 42、73、90 各两条：卷标题 + 卷说明），一律视为「该章第 1 节」：

```
key = 章 * 1000000 + 1 * 10 + 0
```

### 2.3 纲目的层级

`level` 字段直接给出层级，实测分布：

| level | 条数 | 对应编号 |
|---:|---:|---|
| 1 | 307 | 壹 贰 叁 |
| 2 | 894 | 一 二 三 |
| 3 | 1,112 | 1 2 3 |
| 4 | 632 | a b c |
| 5 | 177 | （一）（二） |
| 6 | 19 | （1）（2） |

与 12490 纲目那套编号体系完全一致。

### 2.4 「续」条目

同一个纲目点可能被拆成多条记录，`level_order` 重复，`outline_content` 带「（续）」。例如撒迦利亚 14 章：

```
vo=33  level=3  order=1  1　哈米吉顿大战（续）　十四1～7     起点 14:1
vo=34  level=3  order=3  3　千年国　十四8～11，16～21        起点 14:8
vo=35  level=3  order=1  1　哈米吉顿大战（续）　十四12～15   起点 14:12
vo=36  level=3  order=3  3　千年国（续）　十四16～21          起点 14:16
```

**照搬原文，不去重、不重新编号。** 并且——

> **绝不解析 `outline_content` 里的经文范围文字**（如「十四8～11，16～21」）。
> 范围一律按 2.5 的顺序规则推导。上例按顺序推导得出 1～7 / 8～11 / 12～15 / 16～21，与实际完全吻合。

## 三、切块规则

### 3.1 区间形成（基本单位）

同一卷内按 `volume_order` 排序：

1. 取所有纲目的起点 key；**相同 key 的多条纲目合成一个起点**，归属其中**最深**的那条（`level` 最大；同 level 取 `volume_order` 最大）；
2. 一个区间 = 从某个起点到**下一个起点之前**；本卷最后一个起点到本卷末；
3. **本卷第一个起点之前的经文，并入第一个区间**；
4. 每个区间记录：所属纲目节点，以及从 level 1 到该节点的**完整祖先路径**。

实测区间数 **2,507**，覆盖检查 **未分配 0、重复分配 0**。

> **为什么不用「叶子纲目」作单位**：第一轮模拟用叶子做单位时漏了 15 节经文——有些经文落在父纲目起点与其首个子纲目起点之间，归父节点管，而父节点不是叶子，于是无人认领（雅歌 1:1、列王纪上 17:1、何西阿 5:15~6:3、马太 21:23~27 等）。改用「相邻起点之间的区间」之后，覆盖是**构造性完整**的——不可能有空隙，也不可能重叠。

### 3.2 四条细分规则

```
① 基本单位 = 纲目区间
② 区间字数 > 1,200（约 800 token）→ 按【章】边界切分
③ 切分后某片仍 > 1,200 → 再按【段落】边界切分
④ 仍 > 1,200 → 保留，不再切
```

实测生效次数：②163 个区间、③124 个片、④3 个片。

**不合并短块。** 一条纲目就是一个语义单元，一个字母段、一个跨章的小尾巴，都是完整单元；而且每块的 `text` 都带着完整纲目路径，短块并不缺上下文。

> **「碎片合并」这条规则试过，是错的，已废弃。** 第一轮模拟里加了「字数 < 225 的片并入同区间相邻片」，结果诗篇 119 的 22 个字母段（每段 156～191 字）全部低于阈值，一个接一个往前并，跨过章界把诗 118 到 131 粘成一块 6,353 字，诗 119 连一块独立的都没剩下。全库触发 649 次。取消之后最大块从 6,353 字降到 1,791 字。**不要再加回来。**

### 3.3 三级细分的实际效果

| 例子 | 原字数 | 经过 | 结果 |
|---|---:|---|---|
| 诗篇卷五（107～150 篇） | 16,688 | ② | 44 篇各成一块 |
| 诗篇 119 | 3,801 | ②→③ | 22 块，每块 8 节，正是希伯来字母段 |
| 箴言「智慧行义与愚妄作恶的对比 十1～十九29」 | 6,444 | ② | 10 章 → 10 片 |
| 创世记「以撒的婚娶 二四1～67」 | — | ③ | 5 片 |
| 使徒行传 七2～53（司提反讲论） | 1,791 | ④ | 整段保留 |

诗篇 119 在段落表里**正好是 22 段，起点 1, 9, 17, …, 169**，与 8 节一组完全吻合——恢复本的排印如实记录了字母段。

全书字数 > 1,200 的章共 277 个，其中段落数为 1 的**只有 1 个**（希伯来书 10 章），说明第③步对几乎所有长章都有效，第④步确实只是极少数兜底。

④ 保留的 3 块：

| 卷 | 范围 | 字数 |
|---|---|---:|
| 路加福音 | 六17～49 | 1,213 |
| 使徒行传 | 七2～53 | 1,791 |
| 希伯来书 | 十一2～40 | 1,391 |

最大 1,791 字 ≈ 1,194 token，离嵌入模型的 32,768 上限很远。

### 3.4 卷首块

**每卷一块，66 块**，排在该卷经文块之前，内容是卷名 + 卷主题 + 该卷完整纲目树，**不含经文**。

卷首块**不参与** ②③④ 的字数切分——它是一个整体，拆开就失去意义。最长的（创世记 206 条纲目）估计 3,000 字上下，约 2,000 token，远在上限内。

## 四、text 渲染

### 4.1 经文块

```
〔第一行〕卷名　经文范围
〔纲目路径，每级一行，缩进 = (level − 1) 个全角空格〕
〔若需要，合成的章/篇行，缩进 = 最深层 level 个全角空格〕
〔空行〕
〔经文，每节一行〕
```

例（以弗所书）：

```
以弗所书　一3～6
贰　召会在基督里所得的福分与地位　一3～三21
　一　神给召会的福分　一3～14
　　2　子的救赎，说出神永远定旨的完成　7～12

一3　我们主耶稣基督的神与父，是当受颂赞的，祂在基督里，曾用诸天界里各样属灵的福分，祝福了我们；
一4　就如祂在创立世界以前，在基督里拣选了我们，使我们在爱里，在祂面前，成为圣别、没有瑕疵；
一5　按着祂意愿所喜悦的，预定了我们，借着耶稣基督得儿子的名分，归于祂自己，
一6　使祂恩典的荣耀得着称赞，这恩典是祂在那蒙爱者里面所恩赐我们的；
```

### 4.2 第一行为什么要有卷名

模拟抽样暴露过：以弗所书的块全文里**没有「以弗所书」四个字**，诗篇 119 的块连「诗篇」都没有，只有经节号里带着「一百一十九1」。

这影响两头：检索时「以弗所书讲召会」匹配不上；生成端拿到这块，不知道它出自哪卷。4.0 的约束是「只挑段落、按次序拼接成纲目」，职事纲目历来带出处，**块必须自带身份**。

同一条决定也应用在纲目索引上（见 `chunks_es_plan.md` v0.2），两个索引保持一致。

### 4.3 诗篇的合成层

诗篇整卷只有 10 条纲目（5 条卷标题 + 5 条卷说明），200 个块只有 5 条不同的纲目路径，一条管 44 篇诗。

规则：**当一块的纲目路径最深一层所辖范围跨了多章时，在路径末尾补一行章号。**

- 诗篇写「第一百一十九篇」；
- 其余卷写「第N章」；
- 章号即 `section_code`，直接生成，不需要额外数据；
- 路径本就精确到单章范围的（如以弗所书）不补。

例：

```
诗篇　一百一十九1～8
卷五　第一百零七至一百五十篇
　指明神的家和城成为圣徒的赞美、安全和愿望，并且基督借着神的家和城—召会，来作王治理全地
　　第一百一十九篇

一百一十九1　行径完全，遵行耶和华律法的，这样的人是有福的。
…
```

### 4.4 经节号的写法

`中文章数 + 阿拉伯节号`，与恢复本纲目的写法一致：「一1」「十四8」「一百一十九1」。上/下分节在节号后加「上」「下」：「一2上」「一2下」。

中文章数的转换规则（1→一、11→十一、119→一百一十九）写在 `config.py`，并在建块报告中给出完整对照说明。

### 4.5 卷首块

```
〔卷名〕
主题：〔topic_all_gb_24 的内容〕

纲目：
〔该卷完整纲目树，每级一行，缩进 = (level − 1) 个全角空格〕
```

例（以弗所书，节选）：

```
以弗所书
主题：召会─基督的奥秘，基督的身体，作基督的丰满，成为神的丰满

纲目：
壹　引言　一1～2
贰　召会在基督里所得的福分与地位　一3～三21
　一　神给召会的福分　一3～14
　　1　父的拣选和预定，说出神永远的定旨　3～6
　　2　子的救赎，说出神永远定旨的完成　7～12
…
```

## 五、字段清单

与纲目索引保持同名同义，便于跨索引查询与复用检索代码。

| 字段 | 类型 | 来源 | 建索引 |
|---|---|---|---|
| `chunk_id` | keyword | 见第六节，同时作 ES 的 `_id` | 是 |
| `message_key` | keyword | `bible/{book_no}-{卷名}`，如 `bible/49-以弗所书` | 是 |
| `batch` | keyword | 固定 `bible` | 是 |
| `chunk_type` | keyword | `verses` / `book_outline` | 是 |
| `text` | text | 第四节渲染结果 | 是（ik） |
| `embedding` | dense_vector | 第七节 | 是（knn） |
| `book_title` | keyword + `.text` 子字段 | 卷名，如「以弗所书」 | 是 |
| `book_no` | integer | `chapter_code`，1～66 | 是 |
| `message_title` | keyword + `.text` 子字段 | 该块纲目路径**最深一层**的标题；卷首块填卷名 | 是 |
| `message_number` | integer | 该块的起始章号；卷首块为 `null` | 是 |
| `author` | keyword | 固定「恢复本圣经」 | 是 |
| `verse_range` | keyword | 可读的经文范围，如「一3～6」；卷首块为 `null` | 是 |
| `outline_path` | keyword（数组） | 纲目路径各级的 `outline_content`，含合成层 | 是 |

| `paragraph_type` | keyword | 固定 `bible` | 是 |
| `tokens` | integer | `len(text) / 1.5` | 是 |
| `chunk_index` | integer | 本卷内第几个块，从 1 起（卷首块为 0） | 是 |
| `chunk_total` | integer | 本卷共几个经文块 | 是 |
| `split_rule` | keyword | `none` / `by_chapter` / `by_paragraph` / `keep_oversize` | 是 |
| `source_keys` | integer（数组） | 本块包含的全部经文 key，回查用 | 否 |

### 5.1 `message_title` 为什么填纲目最深层标题

它是这一块最有信息量的名字。检索结果列出来，`message_title` 就是「2　子的救赎，说出神永远定旨的完成」这样一句话，一眼能看懂这块是什么。诗篇那种粗路径的，配上 4.3 的合成层，`message_title` 会是「第一百一十九篇」。

### 5.2 为什么**暂不加**经节坐标字段

曾考虑加 `chapter_start` / `verse_start` / `chapter_end` / `verse_end` 四个数值字段做范围查询。**本版不加**，理由：

它唯一独有的用途是「给定一个经文引用，定位到块」，而那需要先把「—罗三24～25」这类文字解析成结构化经节——正是我们在纲目索引决定不做的解析器。没有解析器，坐标字段没有入口。其余用途（按新旧约过滤、按次序拼接、取相邻块）用 `book_no` + `chunk_index` 就够了。

**这个决定不锁死**：坐标字段不影响 embedding，将来真要做引用解析，连同解析器一起做，用 `update_by_query` 往现有索引补字段即可，**不用重建索引、不用重跑向量**。

### 5.3 不要的字段

`en` / `source_en`（不做英文）、`section_title`（纲目自带层级）、`scripture_refs`（同纲目索引，不做）、`year` / `year_end`（圣经无年份）、`part_no` / `part_name` / `conference` / `month`（纲目索引专用）。

## 六、chunk_id

```
chunk_id = gmbible_{sha1(message_key + "#" + chunk_index) 的前 12 位十六进制}

卷首块 chunk_index = 0
```

与纲目索引同一规则：短 ASCII、同时作 ES 的 `_id`、按 `_id` 覆盖写入即幂等。

**硬性约束**：哈希的输入只能是 `message_key` 与 `chunk_index`，不得掺入总块数、日期等会变的量。

**碰撞**：12 位十六进制 = 48 位空间，3,691 条的碰撞概率可忽略；建块时仍做全量唯一性校验，真撞了立即报错停下。

## 七、向量生成

沿用纲目索引的配置，与 3.5 现行一致：

| 项 | 值 |
|---|---|
| 接口 | OpenRouter |
| 模型 | `qwen/qwen3-embedding-8b` |
| 维度 | 1024 |
| 适配层 | `kg_rag/embedding_adapter.py`，`profile="kg_rag"` |

**embedding 输入 = `text` 本身**，不再另外拼接。因为第四节已经把卷名写进 text 第一行，不需要像早先设计那样临时拼卷名——这样存的和算的完全一致，消除了「改了渲染格式忘了同步 embedding 拼接」这个隐患。

**规模**：3,691 块，按 50 一批 = 74 批，几分钟跑完，成本可忽略。不需要并发。

**试跑**：仍先取 100 条跑通，并单独拿最长的一块（卷首块里最长的那个，估计 3,000 字上下）试一次。纲目索引的试跑已确认 OpenRouter 接受 7,618 token 的单条输入，这边最长也就 2,000 token 左右，风险很低。
